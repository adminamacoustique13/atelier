# Relais P1 — Le pont rapporte les outils refusés, distingue une surcharge d'une limite, et dit si une commande est permise

Copie : `copie-P1`, partie de « Vitesse V5 : le pont lit les limites de l'abonnement et reprend une session » (7b8bca4). Aucun commit.

## Fait, critère par critère

1. **Outils refusés.** `Resultat.refuses: list[str]` (vide par défaut, `compare=False` comme `session`). Le pont (`SessionSDK._tour`) le remplit pour tout tour, quelle qu'en soit l'issue, à partir de trois sources, dans l'ordre où les refus arrivent :
   - ce que le pont décide lui-même dans `can_use_tool` (`_autoriser`, qui enveloppe l'ancien corps devenu `_decider`) : pas de guichet (`SANS_GUICHET`), réponse « non » (dont le délai du guichet), réponse incomprise, guichet en panne. Un refus pour arrêt (message `ARRETE` : arrêt, coupure, `annuler`) n'est pas un outil refusé : l'appel est seulement noté, pour que `permission_denials` ne le compte pas non plus ;
   - les refus de l'arbitre du mode auto lus dans les résultats d'outil (déjà annoncés en événement « refus ») : comptés aussitôt, donc même si le tour finit sans message de fin ;
   - en fin de tour, chaque entrée de `ResultMessage.permission_denials`, **quel que soit le mode**.
   Un même appel (même `tool_use_id`) n'est compté qu'une fois ; une même forme n'apparaît qu'une fois ; vingt entrées au plus (`REFUSES_MAX`). La forme courte vient de la nouvelle `forme_courte(bloc, racine)` (agents), qui réutilise l'objet que calcule `decrire_outil` (factorisé dans `_objet`, `decrire_outil` rend exactement la même chose qu'avant) : « Bash(uv sync) », « Write(b.py) » (chemin à partir du dossier de l'agent), « WebFetch(https://x.y) », ou le seul nom de l'outil ; objet coupé à 120 caractères.
2. **Ouvrier simulé empêché.** `AgentSimule.empeches` (par défaut `{}` : rien ne change). Voir les contrats.
3. **Surcharge.** Nouvelle constante `SURCHARGE` (agents, reprise par sdk), distincte de `LIMITE_ATTEINTE`. Un tour **en échec** dont un signe « rate_limit » (message assistant en erreur `rate_limit`, ou message de fin en erreur) porte le texte d'une surcharge (`est_surcharge` : « not your usage limit » ou « is experiencing high load », sans tenir compte de la casse) rend `SURCHARGE`, sans type ni heure de limite, sans événement « limite ». Un vrai refus vu dans le même tour (événement `rejected`, message `rate_limit` sans ce texte, 429 sans ce texte) l'emporte : `LIMITE_ATTEINTE`. Un tour réussi reste réussi. L'agent simulé joue une surcharge par `limites={"A": ["surcharge"]}`.
4. **`commande_permise(profil, commande) -> bool`** (agents). Les règles d'avance d'un ouvrier sont désormais construites par une seule fonction, `_regles_d_avance(profil, lecture_seule)`, qu'appellent `AgentClaude._outils` (inchangé dans son résultat) et `commande_permise` ; s'y ajoutent les règles retenues du profil (`autorisations`, lues par `_regles_simples` comme pour les agents). La commande est découpée par les expressions du guichet (`CHAINE`, `SUBSTITUTION`, importées, non recopiées) ; chaque morceau doit être couvert comme Claude Code compare une règle Bash (`_couvre`). Redirections, variables, `~` et chemins : voir la seconde passe.
5. **Rien ne change pour les appelants d'aujourd'hui.** Aucune signature ne change ; champs et paramètres nouveaux facultatifs. Seul cas qui change d'issue, voulu : un tour en échec sur une surcharge rendait `LIMITE_ATTEINTE` (type « inconnue »), il rend `SURCHARGE` ; l'événement « fin » porte donc ce texte. Les autres événements sont les mêmes.
6. **Tests.** 71 cas nouveaux (21 fonctions), faux clients existants, aucun appel réel. Tous les tests existants passent sans modification ; ruff vert, complexité 10.

Tests nouveaux, `tests/test_sdk.py` (30 cas) : outil refusé au guichet et outil refusé par le SDK dans `refuses`, sans doublon quand Claude Code reprend le premier dans `permission_denials` ; refus de fin de tour comptés dans les cinq modes ; tour sans refus (et demande autorisée) : liste vide ; ce que le pont refuse lui-même (sans guichet, panne, réponse incomprise) compte, un refus pour arrêt non ; ordre, doublons, borne de vingt ; refus de l'arbitre compté sans message de fin ; pas de débordement sur le tour suivant, entrée mal formée ; surcharge (texte du serveur avec 429, « high load » sans statut, message de fin seul, sans message de fin) ; vraie limite toujours `LIMITE_ATTEINTE` (texte « You've hit your limit », « API Error: 429 », refus annoncé plus surcharge) ; surcharge dans un tour réussi, ou au tour d'avant ; `est_surcharge`.
Tests nouveaux, `tests/test_agents.py` (41 cas) : `forme_courte` ; `AgentClaude` rend `refuses` sans changer l'égalité des résultats, et `SURCHARGE` ; ouvrier simulé non empêché par défaut, empêché (refus, ligne « EMPÊCHÉ : », vérificateur non touché, liste consommée), empêché par plusieurs outils et sur un échec ; surcharge simulée ; `commande_permise` (23 cas : `uv sync` avec et sans `uv`, `uv run …`, `uvx` refusé, socle, git en lecture et en écriture, commandes composées, tube, redirections, `cd`, variable posée devant, `autorisations` exacte et `Bash` seul, profils mal formés), commandes vides ou mal formées (10 cas), et cohérence avec les règles données aux ouvriers.

Preuve que les tests gardent leur règle (mutation faite, test lancé, fichier restauré à l'identique, vérifié par `cmp`) :
- `_couvre` sans l'espace après le préfixe (`uv` couvrirait `uvx`) : `test_commande_permise[profil5-uvx ruff-False]` échoue.
- `_autoriser` qui compte un refus pour arrêt : `test_ce_que_le_pont_refuse_lui_meme_compte_sauf_un_arret[guichet3-attendu3]` échoue.
- `est_surcharge` qui rend toujours faux : 9 tests de surcharge échouent (pont et agent).

## Ce que prouve la lecture du code, et ce qui est supposé

Lu dans le SDK installé (`claude_agent_sdk`, `types.py`, `_internal/message_parser.py`, `_internal/query.py`) et dans le programme Claude Code livré avec lui (`_bundled/claude`, 2.1.308, code minifié lu directement ; les noms entre parenthèses sont ceux du code minifié).

Prouvé par la lecture :
- `permission_denials` : le SDK Python le passe tel quel (`data.get("permission_denials")`). Claude Code le décrit par un schéma `{tool_name: string, tool_use_id: string, tool_input: Record<string, unknown>}` (`xy`). Il le remplit dans le rappel de permission de chaque tour (`Zt`, et `ER`/`recordDenial`) pour toute décision qui n'est pas « allow » (`XKe : behavior !== "allow" && !invalidInput`), une fois par `tool_use_id`. Ce rappel enveloppe tout le chemin de permission, y compris l'appel au `can_use_tool` du SDK : un refus du guichet y revient donc, avec le même `tool_use_id` (d'où le compte par identifiant). Un commentaire du programme dit que `result.permission_denials` est « the authoritative record ».
- `ToolPermissionContext.tool_use_id` est toujours une chaîne non vide quand le SDK appelle `can_use_tool` (docstring du SDK).
- Surcharge, dans le convertisseur d'erreurs de Claude Code : une erreur dont le message contient « Opus is experiencing high load… » ou « Fable is experiencing high load… » donne `{content: "Opus is experiencing high load. Switch to Sonnet." (ou la variante avec /model), error: "rate_limit"}` ; elle naît notamment de l'interrupteur « tengu-off-switch » (`Error(nut)`), sans statut HTTP, donc `api_error_status` absent. Un HTTP 429 pour un abonné (`Urn(vt())`) **sans** en-tête de limite de l'abonnement (`anthropic-ratelimit-unified-representative-claim` ni `anthropic-ratelimit-unified-overage-status`, lus par `hHs`) donne `{content: "API Error: Server is temporarily limiting requests (not your usage limit) · <message du serveur>", error: "rate_limit", apiErrorIsTransient: true}`, et `api_error_status` 429 (`VQ` : `apiErrorStatus = e.status`). Une vraie limite (ces en-têtes présents) donne le texte de `yAo` (« You've hit your limit… », etc.), parfois avec `apiError: "usage_limit_reached"`.
- Ce qui arrive au SDK Python : le message assistant porte `error` (« rate_limit ») et le texte en bloc de texte (`type:"assistant", message, error: y.error`) ; le message de fin d'un tour clos par une erreur d'API porte `is_error`, `result` = le texte de cette erreur, `api_error_status`. Les champs qui distingueraient sans le texte (`apiErrorIsTransient`, `api_error`, `api_error_code`) ne sont pas transmis (`apiErrorIsTransient` n'est pas sérialisé) ou ne sont pas lus par le SDK Python (`AssistantMessage` n'a que `content, model, parent_tool_use_id, error, usage, message_id, stop_reason, session_id, uuid` ; `ResultMessage` n'a pas `api_error`). Le texte est donc le seul signe disponible.
- Le statut 429 seul ne distingue rien : la surcharge et la vraie limite sont toutes deux des 429.
- Règles Bash dans Claude Code : une règle à préfixe `x:*` couvre une commande égale à `x` ou commençant par `x ` (espaces et tabulations ramenés à une espace) ; une commande composée est découpée et chaque sous-commande doit être couverte ; une règle sans `:*` est exacte ; `Bash` seul couvre tout.

Supposé (non prouvé) :
- Qu'aucun événement `rejected` n'accompagne une surcharge (il n'y a pas d'en-tête de limite dans ce cas). S'il y en avait un, le pont rendrait `LIMITE_ATTEINTE` (erreur prudente).
- Que les textes restent ceux de la version 2.1.308 ; une autre version pourrait les changer. Le pont reviendrait alors à `LIMITE_ATTEINTE`, comme avant.
- Que la forme rendue par `permission_denials` et celle vue au guichet coïncident (même `tool_input`) ; si elles différaient, le compte par identifiant évite quand même le doublon.
- (Corrigé en seconde passe : la première version disait vrai à tort pour 13 commandes sur 62.) Claude Code permet aussi de lui-même certaines commandes en lecture (`cd` vers un dossier permis, `echo`…), un préfixe `xargs`, des variables d'environnement sûres posées devant ; `commande_permise` ne les modélise pas et dit faux pour elles. Ce qu'elle dit encore à tort, mesuré : voir la seconde passe.

## Contrats fournis au moteur

`Resultat.refuses: list[str]` (`atelier.agents`) :
- forme courte de chaque outil refusé pendant le tour : `"Bash(uv sync)"`, `"Write(chemin/relatif.py)"`, `"WebFetch(https://…)"`, ou le seul nom (`"TodoWrite"`) ; sans doublon, dans l'ordre d'arrivée, 20 au plus ;
- rempli par `AgentClaude` (tous rôles, et la conversation) et par `SessionSDK.envoyer`, quelle que soit l'issue du tour (succès, échec, limite, surcharge, délai) ; vide pour une reprise demandée d'une session vide et pour un résultat simulé ordinaire ; après un arrêt demandé par `AgentClaude.arreter`, le résultat `ARRETE` est refait à neuf et la liste est vide (ne pas s'y fier) ;
- hors comparaison : `Resultat(...) == Resultat(...)` ne le regarde pas ;
- sources : refus du guichet ou du pont (jamais pour arrêt), arbitre du mode auto, `permission_denials` quel que soit le mode.
- Pour retrouver la commande : l'objet entre les parenthèses de `"Bash(...)"` (la commande sur une ligne, retours à la ligne remplacés par « ; »).

`SURCHARGE` (`atelier.agents`, aussi dans `atelier.sdk`) : `"L'agent a été refusé : Claude est surchargé pour un moment (pas une limite atteinte)."`. À comparer par égalité à `resultat.erreur`. `type_limite == ""`, `fin_limite is None`, `ok` faux, coût et tokens du tour gardés. Aucun événement « limite » n'est émis ; l'événement « fin » porte ce texte. Distinct de `LIMITE_ATTEINTE`, `REPRISE_IMPOSSIBLE`, `ARRETE`, `CLAUDE_SANS_REPONSE`. Fonction publique `est_surcharge(texte) -> bool` (sdk) et constante `SURCHARGES`.

Agent simulé :
- Surcharge : `AgentSimule(limites={"A": ["surcharge"]})` (même liste que les limites, consommée appel après appel, tous rôles, clé `"orchestrateur"` sans tâche) : l'appel rend aussitôt `Resultat(ok=False, erreur=SURCHARGE, session=<session>)`, sans rien écrire, avec le seul événement « fin ».
- Empêché : `AgentSimule(empeches={"B": ["Bash(uv sync)"]})`. Liste par tâche, consommée par les **ouvriers** de la tâche (premier ouvrier, puis le suivant, reprises comprises ; le vérificateur ne la consomme pas). Chaque entrée : une forme courte, une liste de formes courtes, ou `""` (rien). Au-delà de la liste, rien. L'ouvrier empêché suit son scénario (fichiers écrits, verdict du vérificateur, erreur éventuelle) ; son résultat porte `refuses` (les formes, sans doublon), et son `texte` gagne à la fin une ligne par outil : `EMPÊCHÉ : uv sync — l'outil a été refusé : je ne peux pas aller plus loin.` Pour une passe refusée avec empêchement, combiner avec `scenario={"B": ["ne_sait_pas"]}` ; pour un livrable accepté malgré un empêchement, avec `"ok"`. Un ouvrier arrêté rend `ARRETE` sans rien de plus.

`commande_permise(profil: dict, commande: str) -> bool` (`atelier.agents`) :
- vrai si un ouvrier pourrait lancer la commande sans rien demander, d'après le socle (`COMMANDES_DEV`, `LECTURE_SHELL`, `GIT_LECTURE`), `profil["commandes_permises"]` (chaque mot `x` donne `Bash(x:*)`) et `profil["autorisations"]` (règles retenues « toujours pour ce projet ») ; les règles du chantier en cours n'y sont pas ;
- chaque morceau d'une chaîne (`&&`, `||`, `;`, `|`, `&`) doit être couvert ;
- le mode des ouvriers est lu dans `profil["mode_ouvriers"]` par `lire_mode` (« acceptEdits » s'il manque), comme le font les agents ; le serveur y écrit le mode choisi ;
- redirections : passent `2>&1`, `>&2` (un descripteur), `/dev/null` (dans les deux sens), `< fichier` dans la copie, et `> fichier`, `>>`, `&>` vers un fichier de la copie **seulement en mode « acceptEdits »** ; toute autre redirection (hors de la copie, `..`, `~`, `<<`, `<<<`, cible vide ou à caractères douteux) rend faux ;
- faux dès qu'un `$` apparaît (même entre apostrophes) ou un `~` en début de mot (ou après `=`, `:`, un guillemet) ;
- pour les commandes dont Claude Code vérifie les chemins (`CHEMINS_VERIFIES`, sa table : cat, ls, grep, head, tail, wc, diff, git, mkdir, touch, jq, sha256sum…), faux si un argument est absolu ou remonte par `..`, même comme valeur d'option (`--x=/y`) ; pour les autres (pytest, python, ruff, make, uv…), Claude Code ne regarde pas les chemins et la fonction non plus ;
- faux pour : une commande qui n'est pas une chaîne, vide, avec substitution (`$(`, accent grave, `<(`, `>(`) ou caractère de contrôle (dont un retour à la ligne), un morceau vide (`a &&`, `;;`), un `cd`, une variable posée devant, et tout ce que ces règles ne couvrent pas ;
- elle ne dit jamais vrai là où le vrai Claude Code demande, sur les 106 commandes essayées dans les deux modes ; elle dit encore faux à tort dans quelques cas (seconde passe) ;
- exemples : `commande_permise({}, "uv sync")` faux ; `commande_permise({"commandes_permises": ["uv"]}, "uv run pytest -q")` vrai ; `commande_permise({}, "ruff check . && pytest -q")` vrai.
- Pour le contrôle à la validation (fiche V3b, décision 6) : appeler `commande_permise(profil, c)` pour chaque `c` de `profil["commandes"]` ; c'est plus large que « le premier mot » (une commande composée est vérifiée en entier).

Autres noms publics nouveaux : `forme_courte(bloc, racine=None)`, `REFUSES_MAX`, `OBJET_MAX` (agents).

## Doutes
1. **Texte en anglais.** La distinction repose sur le texte de Claude Code, faute d'autre signe transmis au SDK Python. Une version de Claude Code qui changerait ces phrases ferait revenir la surcharge à `LIMITE_ATTEINTE` (comportement d'avant, prudent). À revoir à chaque mise à jour du SDK.
2. **Autres « rate_limit » qui ne sont pas des limites.** Le blocage par modèle « tengu-model-error-overrides » rend aussi `error: "rate_limit"` avec un texte fourni par le serveur, inconnu d'avance : il reste `LIMITE_ATTEINTE` type « inconnue ». Un 429 pour une clé API (« Request rejected (429) · this may be a temporary capacity issue ») aussi : je n'ai pas élargi au-delà des deux textes demandés.
3. **`commande_permise` dit parfois faux à tort.** Pour `cd sous && pytest`, `echo`, `grep -r 'a|b' .`, `pytest ~/x`, que Claude Code laisse passer (liste mesurée en seconde passe). Le serveur poserait alors une question de trop ; il faudra que la question ne propose pas de permettre `cd`. (La première version ignorait les redirections et disait vrai à tort : corrigé en seconde passe.)
4. **Refus du guichet par absence de réponse.** Le délai du guichet ferme sur « non » (`SANS_REPONSE`) : l'outil est compté comme refusé. C'est vrai, mais le moteur ne doit pas y voir un empêchement à lui seul quand la personne était simplement absente ; à trancher dans `refus.py`.
5. **Refus en mode plan.** Le mode plan (répétition) peut être choisi pour les ouvriers. Si un ouvrier y tente un outil qui change quelque chose, ou si la personne refuse son passage à l'exécution (`ExitPlanMode` au guichet), ces refus arrivent dans `refuses` sans être des empêchements. Supposé d'après la règle `XKe`, non vérifié avec le vrai Claude Code.
