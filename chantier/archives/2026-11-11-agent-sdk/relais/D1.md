## 3. Contrats modifiés

**Dans la vue** (`GET /api/etat` et toute réponse de route) :
```json
"autorisations": [
  {"id": "d1-77f4858d", "agent": "B-ouvrier-1", "outil": "Bash",
   "phrase": "B-ouvrier-1 veut lancer la commande « npm install left-pad ».",
   "regle": "Bash(npm install:*)", "detail": "npm install left-pad"}
],
"agents": [
  {"nom": "B-ouvrier-1", "tache": "B", "role": "ouvrier",
   "lignes": ["Lit la consigne", "En attente de ton autorisation : Lance npm install left-pad"]},
  {"nom": "orchestrateur", "tache": "", "role": "orchestrateur", "lignes": ["J'ai découpé ton objectif"]}
]
```
- `autorisations` : `guichet.ouvertes()` tel quel, six chaînes par demande ; `[]` sans guichet. Le bouton « toujours » est à masquer quand `regle` est vide. `detail` est le texte complet.
- `agents` : chaque agent en marche (un événement « fin » le retire), dans l'ordre d'arrivée ; `lignes` : au plus 30, de 300 caractères au plus ; la dernière peut être une ligne en cours d'écriture. `tache` est vide pour l'orchestrateur. Une ligne d'attente commence par « En attente de ton autorisation : ».
- Le `point_d_etape` ajoute « J'ai besoin de toi pour 1 autorisation. » (ou « 1 décision et 2 autorisations. ») quand une demande est ouverte.
- Sans projet (`aucun_projet`), la vue de `Projets.vue` n'a ni `autorisations` ni `agents` : le tableau de bord doit lire `vue.autorisations || []`.

**`POST /api/autorisation`** : `{"id": "d1-77f4858d", "choix": "une_fois" | "toujours" | "non", "message": ""}` (`message` facultatif). Réponse 200 : la vue, plus
```json
"autorisation": {"reglee": true, "phrase": "Autorisé pour ce projet : la règle Bash(npm install:*) est enregistrée dans le profil."}
```
Phrases possibles : « Autorisé cette fois. », « Refusé. », celle ci-dessus, « Autorisé cette fois, mais la règle n'a pas pu être enregistrée : ... » (réglée quand même), et pour `"reglee": false` : « Cette demande n'existe plus : elle a déjà reçu une réponse, ou son agent s'est arrêté. », « Aucune règle sûre n'existe pour cette demande : autorise-la une fois, ou refuse-la. » (la demande reste ouverte), « Ce choix n'existe pas : réponds « une fois », « toujours » ou « non ». ». Corps sans `id` ou `choix`, ou qui n'est pas un objet : 400 `{"erreur": "Demande introuvable ou incomplète."}`.

**`POST /api/arreter`** : `{"tache": "B"}`, ou `{}` pour l'orchestrateur. Réponse 200 : la vue, plus
```json
"arret": {"fait": true, "phrase": "Arrêt demandé pour la tâche B."}
```
Autres phrases : « Arrêt demandé : la réponse en cours s'arrête. », « La tâche B n'est ni en cours ni en vérification : rien à arrêter. », « L'orchestrateur ne répond à rien en ce moment : rien à arrêter. ». `fait` dit que l'arrêt est demandé : la tâche revient quelques instants plus tard (le temps que l'agent sorte).

**Une tâche arrêtée** : état « revenu », décision `« Tâche B, « titre » : arrêtée par toi. »` aux trois options habituelles (`Relancer au même niveau`, `Relancer un cran plus haut`, `Abandonner cette tâche`) ; dernière entrée d'historique `{"issue": "arretee", "detail": "Arrêtée par la personne responsable."}`, dans tous les cas : si l'arrêt vient avant qu'un ouvrier ne parte (tout début de boucle, ou pendant la préparation), l'entrée porte le numéro de la tentative qui n'a pas eu lieu (par exemple « Tentative 2 » après un refus). Le tableau de bord (fiche de tâche) affiche toute issue différente de « valide » comme un échec : D2 peut vouloir un libellé propre pour `arretee`.

### À savoir pour la tâche D2
- `arret.fait` à `true` ne garantit pas que la tâche reviendra tout de suite : l'agent met un instant à sortir. C'est l'état de la tâche dans la vue (`en_cours`, `en_verification`, puis `revenu`) qui fait foi.
- Le motif de l'arrêt se lit dans la question de la décision (« ... : arrêtée par toi. »).
- `autorisations[].agent` correspond à `agents[].nom` : une carte d'agent peut afficher la demande qui l'attend.
- L'activité n'est jamais poussée : le tableau de bord interroge `/api/etat`.
- Le bouton d'arrêt d'une tâche n'a de sens que dans les états `en_cours` et `en_verification`. Dans les autres, ou si la tâche vient d'être acceptée, la route répond `fait: false` avec une phrase à afficher telle quelle.
- Sans projet ouvert, la vue n'a ni `autorisations` ni `agents`.
- La phrase d'une autorisation (`phrase`) est coupée à 160 caractères ; `detail` porte le texte complet.

**Moteur** : `Moteur.arreter(identifiant) -> bool` (False si la tâche n'est ni en cours ni en vérification, ou si elle est déjà acceptée), `Moteur.enregistree(identifiant) -> bool` ; motif `"arretee"` ; constantes `ARRETEE`, `MOTIF_ARRET`, `DETAIL_ARRET`. **Serveur** : `Atelier(..., guichet=None)`, `Atelier.autoriser(id, choix, message="") -> dict`, `Atelier.arreter(tache=None) -> dict`, `Atelier.activite` (`Activite.ajouter`, `Activite.agents`), `point_d_etape(..., autorisations=0)` et `vue(..., autorisations=0)`. Les routes sont maintenant une table `ROUTES` (les routes existantes et leurs réponses ne changent pas).

## 5. Doutes et demandes
- **Reste de la course de l'arrêt.** Entre la dernière relecture du drapeau et l'inscription de l'agent dans `agent.executer`, il reste quelques instructions : un arrêt qui tomberait exactement là serait pris par la relecture suivante (après l'agent). Rien de lent ne s'y intercale.
- **Première réponse arrêtée.** La session est gardée, comme demandé. Si Claude Code n'avait pas encore écrit sa session quand l'arrêt est venu, la reprise au message suivant pourrait échouer. Le faux client ne peut pas le montrer : c'est un point de la tâche F.
- Un arrêt demandé sans le moteur (directement sur l'agent) est reconnu à l'erreur « Arrêté par la personne responsable. » du `Resultat`, comme le veut la fiche C ; le motif est alors le même.
- Un agent dont aucun « fin » n'arrive resterait affiché : le pont et les agents émettent toujours exactement un « fin », je n'ai pas ajouté d'autre garde.
- Aucune demande hors périmètre.
