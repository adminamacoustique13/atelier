# Relais V5 — Le pont lit les limites de l'abonnement et sait reprendre une session

Copie : `copie-V5`, partie de « Chantier : l'objectif vitesse entre au contrat ; cahier à jour » (5cb72b4). Aucun commit.

## Fait, critère par critère

1. **Limites.** `SessionSDK._suivre` lit désormais les `RateLimitEvent` du SDK (`_suivre_limite`, traduction par la fonction publique `lire_limite`). Une alerte (`allowed_warning`) ou un refus (`rejected`) donne un événement de genre « limite » par `sur_evenement` ; rien ne s'arrête à ce moment-là. Le jugement se fait à la fin du tour (`_qualifier`) : un tour **en échec** pendant lequel une limite a été refusée (événement `rejected`, ou message assistant en erreur `"rate_limit"`, ou résultat en erreur avec `api_error_status == 429`) rend `LIMITE_ATTEINTE`, avec `type_limite` et `fin_limite`. Un tour réussi reste réussi, même après un `rejected` (voir les suppositions). L'arrêt et le délai dépassé gardent leur erreur, avant toute qualification.
2. **Agent simulé, limites.** Champ `limites` (par tâche, une liste consommée appel après appel : `"refus"`, `"alerte"`, `""`), `type_limite` et `delai_limite_s`. Par défaut, liste vide : rien ne change (vérifié par un test, et par le test d'égalité existant).
3. **Reprise.** `AgentClaude.executer(..., reprendre=<session>)` ouvre la session du pont avec `session=<id>, reprise=True` (déjà traduits en `resume=<id>` par `_fabriquer`, comme pour la conversation de l'orchestrateur) et le nouveau `reprise_exigee=True`. La consigne passée est le message de plus (le verdict) ; le dossier est celui que l'appelant donne. Si la session ne peut pas être reprise, le résultat a pour erreur `REPRISE_IMPOSSIBLE` et rien d'autre n'est tenté (une seule connexion). Sans `reprendre`, les options sont exactement celles d'aujourd'hui (`session_id=None, resume=None`). Tout résultat d'`AgentClaude` porte `session` (l'identifiant lu dans `init` ou le message de fin).
4. **Agent simulé, reprise.** Chaque appel rend une session (`session-simulee-<n>`). `reprendre=<session rendue>` note `{"tache", "role", "tentative", "session", "message"}` dans `agent.reprises`, ajoute `"reprise": <session>` à l'entrée de `agent.appels`, et rend la même session. Session inconnue, ou oubliée par `oublier_sessions()` : `REPRISE_IMPOSSIBLE`.
5. **Rien ne change pour les appelants d'aujourd'hui.** Paramètres nouveaux facultatifs et placés en dernier (`reprendre`, `reprise_exigee`). Champs nouveaux de `Resultat` avec valeur par défaut ; `session` est hors comparaison (`compare=False`), donc les égalités de résultats d'aujourd'hui tiennent. Mêmes événements tant que le SDK n'émet aucun événement de limite (avant, ils étaient ignorés). Modes et arrêt inchangés.
6. **Tests nouveaux** (faux client de `tests/test_sdk.py`, aucun appel réel) : 26 cas (16 fonctions) dans `tests/test_sdk.py`, 17 cas (14 fonctions) dans `tests/test_agents.py`. Refus pour limite (type, heure, événement, fin), refus suivi d'une panne ou d'aucune réponse, signalement sans événement (`rate_limit`, 429), alerte qui laisse le travail continuer, refus suivi d'un succès, alerte suivie d'un échec ordinaire, état d'un tour qui ne déborde pas sur le suivant, `lire_limite`, `decrire_limite` ; reprise dans la bonne session, le bon dossier et avec le bon message, reprise impossible (fin en erreur, exception, aucune réponse, connexion refusée, autre session annoncée au départ, coupée aussitôt sans passer au guichet), échec ordinaire une fois la session reprise, conversation sans reprise exigée inchangée, arrêt pendant une reprise ; l'agent simulé dans chacun de ces cas ; appel d'aujourd'hui identique.
7. 820 tests existants verts sans modification ; ruff vert (complexité 10) ; `python -m atelier demo --port 18765` démarre et sert la page (code 200).

## Ce que prouve la lecture du SDK (0.2.172), et ce qui est supposé

Prouvé par la lecture :
- `types.py` l. 1745-1792 : `RateLimitEvent(rate_limit_info, uuid, session_id)` ; `RateLimitInfo(status, resets_at, rate_limit_type, utilization, overage_status, overage_resets_at, overage_disabled_reason, raw)` ; `status` parmi `allowed`, `allowed_warning`, `rejected` ; `rate_limit_type` parmi `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `overage`. Le docstring : l'événement est émis à chaque changement d'état ; `resets_at` est un « Unix timestamp ». Les deux classes sont exportées par `claude_agent_sdk`.
- `_internal/message_parser.py` l. 356-376 : le message `rate_limit_event` du CLI devient `RateLimitEvent` (`resetsAt`, `rateLimitType`, `utilization`…). Il arrive donc dans `receive_response` comme les autres messages.
- `types.py` l. 1277-1284 : `AssistantMessage.error` peut valoir `"rate_limit"`.
- `types.py` l. 1713-1716 : `ResultMessage.api_error_status` donne le statut HTTP (429 cité en exemple) quand `is_error` est vrai.
- `_errors.py` et `_internal/query.py` l. 510-560 : après un résultat en erreur, le CLI sort en échec ; le SDK remplace alors la `ProcessError` par une `ResultError` (avec `api_error_status`, `terminal_reason`, `session_id`), mise dans le flux puis levée par `receive_messages`. Le commentaire l. 540-543 dit qu'un résultat en erreur pendant l'initialisation, « par exemple une reprise refusée », fait échouer `connect` avec cette erreur.
- `_internal/transport/subprocess_cli.py` l. 643-655 : `resume` devient `--resume=<id>`, `session_id` devient `--session-id=<id>`. `_internal/sessions.py` : les sessions sont rangées par dossier de projet, trouvé à partir du chemin du dossier.

Supposé (non prouvé par la lecture) :
- Qu'un agent refusé pour limite reçoive l'événement `rejected` (ou l'un des deux signes) avant la fin en échec. Si Claude Code refusait sans aucun de ces trois signes, le refus resterait une erreur ordinaire.
- Que `resets_at` soit en secondes. Garde-fou : une valeur au-delà de 1e11 est lue comme des millisecondes.
- Qu'un statut 429 soit toujours une limite (abonnement ou débit de l'API) ; son type est alors « inconnue », sauf si un événement l'a nommé.
- (Corrigé en seconde passe : le dépassement payant se lit désormais, voir plus bas.) Un échec pour une tout autre raison après un vrai `rejected`, sans dépassement payant, sera lu comme un refus pour limite.
- Qu'une session reprise sans `fork_session` garde son identifiant dans le message `init`. Si c'était faux, toute reprise rendrait `REPRISE_IMPOSSIBLE` : l'appelant repartirait de zéro, comme aujourd'hui, au prix d'une connexion perdue.
- Que la reprise exige le même dossier (déduit du rangement des sessions par projet). Le pont ne le vérifie pas : c'est à l'appelant de redonner le même dossier.
- Le texte exact d'une reprise refusée (« No conversation found… ») n'est pas lu : le pont s'appuie seulement sur « échec avant que la session ait répondu ».
- En mode flux (`ClaudeSDKClient`), on ne sait pas si le CLI sort après un résultat en erreur : les deux cas (message de fin, exception) sont traités.

## Contrats fournis à la tâche suivante (le moteur)

Constantes, dans `atelier.agents` (reprises par `atelier.sdk`) ; on les compare par égalité à `resultat.erreur` :
- `LIMITE_ATTEINTE = "L'agent a été refusé : une limite de l'abonnement Claude est atteinte."`
- `REPRISE_IMPOSSIBLE = "La session de la tentative précédente ne peut pas être reprise."`
- `LIMITE_INCONNUE = "inconnue"` (le type d'une limite que le SDK ne nomme pas).
- Distinctes de `ARRETE` (`atelier.guichet`) et de `CLAUDE_SANS_REPONSE` (`atelier.sdk`).

`Resultat` (champs nouveaux, tous facultatifs) :
- `type_limite: str` — `""` hors refus ; sinon `five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `overage` ou `inconnue`.
- `fin_limite: float | None` — heure de levée de la limite en secondes Unix (comparable à `time.time()`), None si le SDK ne la donne pas.
- `session: str` — identifiant de session de l'agent, `""` s'il est inconnu ou si la reprise a échoué. Hors comparaison.
- Un refus pour limite garde `cout_usd` et `tokens` du tour ; `ok` est faux.

Événement d'une limite, par `sur_evenement` (même canal que « texte », « outil », « fin ») :
`{"agent": nom, "type": "limite", "contenu": phrase en clair, "statut": "alerte" | "atteinte", "limite": type comme ci-dessus, "fin": float | None (secondes Unix), "utilisation": float | None (0 à 1)}`.
« alerte » : limite proche, le travail continue. « atteinte » : le SDK a dit `rejected` sans que le dépassement payant prenne le relais ; le résultat dira si l'agent a été refusé. Pendant le dépassement payant (`depassement_en_service`), aucun événement « limite » n'est émis, et un échec garde son erreur ordinaire. La phrase vient de `decrire_limite(statut, type_limite, fin=None, utilisation=None)`.

Reprise :
- Demander : `agent.executer(verdict, modele, effort, meme_dossier, False, contexte, reprendre=resultat_precedent.session)`. Les autres arguments sont ceux d'un ouvrier ordinaire ; le mode des ouvriers s'applique comme toujours.
- Lire la session : `resultat.session` (AgentClaude et AgentSimule, tous rôles).
- En cas d'échec : `resultat.erreur == REPRISE_IMPOSSIBLE` ; rien n'a été tenté à la place, à l'appelant de repartir de zéro.
- `reprendre=None` (ou absent) : pas de reprise, session neuve. `reprendre=""` (ou une chaîne d'espaces) : reprise demandée d'une session inconnue, donc `REPRISE_IMPOSSIBLE` aussitôt, sans lancer d'agent (seul un événement « fin » est émis), dans le vrai agent comme dans le simulé. On peut donc passer `reprendre=resultat.session` sans le tester avant.
- Au pont directement : `SessionSDK(..., session=id, reprise=True, reprise_exigee=True)`.

Agent simulé :
- `AgentSimule(limites={"A": ["refus"]})` : le premier appel à `executer` pour la tâche A (tout rôle) est refusé aussitôt pour limite (événements « limite » `atteinte` puis « fin »), sans rien écrire ; les appels suivants suivent le scénario. `"alerte"` : événement « limite » `alerte`, puis le travail prévu. `""` : rien. Clé `"orchestrateur"` pour un appel sans tâche. La liste est consommée par appel, indépendamment du numéro de tentative.
- `type_limite` (défaut `"five_hour"`) et `delai_limite_s` (défaut 3600 ; None : heure inconnue, `fin_limite` None).
- `reprendre=<session rendue>` : noté dans `agent.reprises` (`{"tache", "role", "tentative", "session", "message"}`) et dans `agent.appels[-1]["reprise"]` ; même session rendue. Session inconnue : `REPRISE_IMPOSSIBLE`, rien n'est noté dans `reprises`. `agent.oublier_sessions()` rend impossibles les reprises des sessions déjà rendues.

## Doutes
1. La conversation de l'orchestrateur passe aussi par le pont : si elle est refusée pour limite, son erreur devient `LIMITE_ATTEINTE` au lieu du texte brut du SDK. Le serveur l'affiche après « Je n'ai pas pu joindre Claude Code. » ; il n'y a pas d'autre effet (il ne compare l'erreur qu'à `ARRETE`). Ce n'est pas une reprise exigée : un échec de reprise de la conversation garde son erreur d'aujourd'hui.
2. Un refus vu pendant un tour qui échoue ensuite pour une autre raison sera dit « limite » : erreur prudente, puisque l'appelant attendra plutôt que de monter de modèle.
3. Si la supposition sur l'identifiant d'une session reprise est fausse, toute reprise rendra `REPRISE_IMPOSSIBLE`. À contrôler une fois avec le vrai Claude Code, sans quoi le levier 3 ne donnera rien (mais ne cassera rien).

## Seconde passe

Deux défauts recalés par le vérificateur ; rien d'autre n'a été touché.

1. **Dépassement payant lu comme un refus.** Ce que dit la lecture :
   - le SDK donne `RateLimitInfo.overage_status` (`overageStatus` du CLI) et `RateLimitInfo.raw`, le message entier (`types.py` l. 1769-1776, `message_parser.py` l. 360-368) ;
   - le programme livré avec le SDK (`_bundled/claude`, 2.1.308, code minifié lu directement) calcule le champ `isUsingOverage` du `rate_limit_event` ainsi : `isUsingOverage: status === "rejected" && (overageStatus === "allowed" || overageStatus === "allowed_warning")`. Ailleurs, le même programme traite `status !== "rejected" || isUsingOverage === true` comme « pas bloqué ». Le SDK ne modélise pas `isUsingOverage` : on ne le trouve que dans `raw`.
   Ce qui a changé : nouvelle fonction publique `depassement_en_service(info)` (`sdk.py`). Elle est vraie si `raw["isUsingOverage"] is True`, ou si `status == "rejected"` et `overage_status` vaut `allowed` ou `allowed_warning`. Dans ce cas, `_suivre_limite` n'émet rien et ne compte pas de refus. Un refus vu plus tôt dans le même tour est effacé, puisque les requêtes passent de nouveau. Un échec qui suit garde son erreur ordinaire (par exemple « Reached max turns »). Je n'émets pas d'alerte à ce moment-là : Claude Code renvoie cet état à chaque agent pendant toute la période, et le moteur aurait réduit les places pour rien. Le signe d'un 429 ou d'une erreur assistant `rate_limit` reste un refus.
   Tests : travail normal sans aucun événement (dépassement lu par `overage_status` puis par `raw`), échec banal qui garde son erreur, dépassement qui efface un refus du même tour, `depassement_en_service` (7 cas).
2. **`reprendre=""`.** `AgentClaude.executer` distingue désormais `None` (pas de reprise) d'une chaîne vide ou faite d'espaces : `REPRISE_IMPOSSIBLE` aussitôt, aucun client créé, un seul événement « fin ». `AgentSimule` le faisait déjà (une session vide n'est jamais rendue) ; c'est maintenant vérifié par un test. Tests : 2 cas pour le vrai agent, 2 pour le simulé.

Contrats : précisés ci-dessus (événement « limite », reprise d'une session vide, nom public `depassement_en_service`). Aucune signature ne change.
