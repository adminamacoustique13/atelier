# Fiche de relais V2 : les niveaux de vérification et le dosage de départ

Copie de travail partie de 5cb72b4 (« Chantier : l'objectif vitesse entre au contrat ; cahier à jour »). Rien n'est commité.

## Fait

1. **Le niveau de vérification par type.** `atelier/dosage.py` porte trois constantes, `COMPLETE = "complete"`, `BORNEE = "bornee"` et `MECANIQUE = "mecanique"` (réunies dans `NIVEAUX`), et une table `NIVEAU_DEPART` :
   - `delicate`, `physique` (la norme de calcul), `conception` et `reparation` : `complete` ;
   - `courante` : `bornee` ;
   - `mecanique` : `mecanique`.

   La fonction `niveau_verification` rend ce niveau. Un type inconnu reçoit `complete`. Chaque niveau a sa phrase en français (`NIVEAUX_FR`), que rend `libelle_niveau(niveau)`. Un niveau inconnu y est lu comme la vérification complète.

   Ce que j'ai trouvé dans le module et dans la consigne de l'orchestrateur : cinq types, `mecanique`, `courante`, `delicate` (sécurité, contrat entre modules), `physique` (formule ou norme) et `conception`. Il n'existe **ni type « réparation » ni type « documentation »**.
   - La réparation est une tâche que le moteur ajoute seul. Elle a le type `courante` et un identifiant qui commence par `REPARATION-` (`moteur.PREFIXE_REPARATION`). J'ai donc ajouté le paramètre `reparation=False` : quand il vaut vrai, la tâche est lue sous la clé `"reparation"`, toujours en vérification complète. `dosage.py` n'importe pas `moteur.py`, qui l'importe déjà.
   - La documentation entre dans `mecanique`, puisque la consigne y range les textes. Je n'ai pas créé de type `documentation`, car le moteur refuse tout type absent de `TYPES_FR`.
   - La conception n'était pas dans la table demandée. Je lui ai donné `complete` (dans le doute, on vérifie), sans plancher : le profil peut la baisser.
2. **Le réglage par le profil.** La clé du profil s'appelle `verification`. Elle a la même forme que `dosage` : un dictionnaire type → valeur, par exemple `{"courante": "complete", "mecanique": "bornee"}`. La lecture est tolérante, comme `lire_mode` et `lire_delai` : une clé qui n'est pas un dictionnaire, ou une valeur qui n'est pas exactement l'un des trois niveaux, est ignorée sans erreur. Le plancher `PLANCHER_COMPLET = {"delicate", "physique", "reparation"}` garde ces types en `complete` quoi que dise le profil. Le profil peut aussi régler un type inconnu.
3. **Le vérificateur selon le niveau.** La fonction nouvelle est `verificateur_selon_niveau(modele, effort, niveau)`. Ce qu'elle rend :
   - en `complete`, exactement `verificateur(modele, effort)` ;
   - en `bornee`, le même modèle que l'ouvrier, au même effort, sans descendre sous l'effort moyen (le même plancher que `verificateur`) ;
   - en `mecanique`, `None` ;
   - pour un niveau inconnu, le résultat complet.

   Un modèle hors de l'échelle lève `ValueError`, comme aujourd'hui. `dosage.verificateur` n'a changé ni de signature ni de résultat.
4. **Le départ du type mécanique.** `DEPART["mecanique"]` vaut maintenant `("sonnet", "low")` ; c'était `("haiku", "low")`. Plus aucun type ne part sur Haiku. **J'ai trouvé Haiku en bas de l'échelle `MODELES` et je l'y ai laissé.** Le retirer aurait changé `monter`, `dans_plafond`, des contrats existants dont le plafond est Haiku, et le coût simulé d'`agents.py`. Il reste joignable par un plafond, par la clé `dosage` d'un profil ou par une montée depuis lui. L'échelle de montée reste la même : haiku < sonnet < opus < fable.
5. **Les tests** sont dans `tests/test_dosage.py`, en 15 fonctions nouvelles (23 cas avec le paramétrage). Ils couvrent la table, le type inconnu, la réparation, le réglage par le profil, le plancher (un profil qui demande « mecanique » pour `delicate` reçoit « complete »), neuf réglages mal formés, la phrase de chaque niveau, le vérificateur à chaque niveau, le modèle hors échelle et l'appel d'aujourd'hui inchangé.
6. Tous les tests passent (843) et le contrôle de forme est vert. Le mode démonstration démarre : « Tableau de bord de démonstration : http://127.0.0.1:8791 ». Le moteur n'appelle aucune fonction nouvelle. Le seul changement de comportement qu'il voit est le départ Sonnet du type mécanique, que le critère 4 demande.

- Les niveaux : `dosage.COMPLETE = "complete"`, `dosage.BORNEE = "bornee"`, `dosage.MECANIQUE = "mecanique"`, et `dosage.NIVEAUX = ("complete", "bornee", "mecanique")`.

## Doutes
- **Écart au critère 4 sur deux tests de `test_moteur.py` (l. 609 et 621).** Ils éprouvent la relance seule « un cran plus haut » à partir d'un départ Haiku sous le plafond par défaut, Opus en effort élevé. Avec un départ Sonnet, la relance viserait Fable, au-dessus de ce plafond. Elle n'aurait donc plus lieu, et accorder les seules valeurs attendues aurait vidé ces tests de leur sens. J'ai relevé le plafond de ces deux chantiers d'essai à Fable, effort élevé, pour garder ce qu'ils éprouvent. C'est un changement de mise en place, pas de valeur attendue. À valider.
- **`test_serveur.py`** n'est pas nommé dans le critère 4, mais son test du coût dépend du dosage par défaut (Haiku à 0,02, Sonnet à 0,09). Je n'ai accordé que la valeur et son commentaire.
- La leçon « Le dosage des modèles » veut Fable pour une vérification complète. Le critère 3 demande « un modèle au-dessus de l'ouvrier, comme aujourd'hui ». J'ai suivi le critère 3. Ce désaccord est à trancher avant de brancher le moteur.
- En vérification bornée, j'ai gardé le plancher d'effort moyen de `verificateur`. Le « même modèle » ne veut donc pas toujours dire « même effort » : un ouvrier Sonnet en effort faible est vérifié par Sonnet en effort moyen.
- La conception est en `complete` sans plancher : c'est mon choix, la table demandée n'en disait rien.
- Le départ Sonnet coûte un peu plus par tâche mécanique, comme le diagnostic l'annonce (levier 8).
